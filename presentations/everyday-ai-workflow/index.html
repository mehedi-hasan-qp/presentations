eqc-kit · The commands

What you run,
and where AI is used

CommandWhat it doesUses AI?
/eqc-checkChecks every rule, with the file as proofYes (a plain script sets the level)
/eqc-fixSuggests fixes, easiest wins firstYes
eqc guardFails if a rule that passed stops passingNo
verify + git hooksOptional: runs a command like npm run lint on commitNo
Four things you run. The top two use AI, the bottom two don't. /eqc-check: the first time, one agent reads your standard and lists every rule by tier. Then one agent per tier goes through the code, in parallel. Each rule gets pass, partial, fail or not applicable, with the file as proof. CUTTABLE if running late — If you already have a code map, like a graphify graph, it looks there first, but only if the map is newer than your last commit and your uncommitted changes. It never builds or refreshes the map for you, and anything it finds there it confirms in the real code. Then a plain script, no AI, works out the level: the highest tier where that tier and every tier below it have no fails. A fail in the lowest tier is HARD_FAIL. The script never reads your code; it just counts the answers. It writes the report as Markdown, and next to it an HTML page. One file, no JavaScript, you just open it in the browser. /eqc-fix: it ranks what to fix, low effort and high gain first. Small stuff goes to one fixer. Bigger stuff: opus writes a plan, you approve it, and cheaper models do the typing. It asks before touching CI, packages, architecture or the top tier, it only runs one fixer at a time, and it never commits for you. guard: this is the answer to "AI fixed it, then broke it again". Every time results are saved, it remembers which rules passed. That's the baseline, and it only goes up. Guard fails if one of those rules stops passing, or the level drops. A rule that was already failing won't block you. verify: some rules a plain command can check, like "lint is clean". Those rules carry a command, like npm run lint. The script runs them only for rules that are passing, so a known fail never blocks a commit; only a regression does. CUTTABLE if running late — Not every rule gets one, only the ones a command can check without judgment. CUTTABLE if running late — hooks: opt-in, one command per clone, npx eqc-kit hooks. Commit runs verify; push runs verify, then guard. It won't override hooks you already have, like Husky; it prints the lines to add instead. Anyone can skip hooks with --no-verify, so put the same two commands in CI. Why no AI in the hooks? Too slow, costs money on every commit, and you'd get a different answer each time. /orchestrate · How it works

How /orchestrate runs a big task,
phase by phase

The orchestrator plans and checks. Helpers on haiku, sonnet or opus write the code.

PhaseWhat it does
GRILLAsks you questions, one at a time
PLANSplits the goal into scored tasks
PREVIEW · the gateShows the plan, waits for your OK

Five phases. The slide keeps it short; I'll add the detail as I go. GRILL is the interview I used to ask for by hand. One question at a time, each with a recommended answer, so most of the time I just say yes. If you have a code map, its helpers search that before grepping. Tiny goals take a fast lane and skip this. PLAN: it splits the goal into tasks and scores each one. Scoring is the next slide. At most 3 helpers run at once, and each file has one owner, so they don't step on each other. PREVIEW is the part I care about most. It shows every task with its score and model, then stops. Only my reply counts: "just go" written into the goal is ignored, and "ok, but…" counts as an edit. I'll show you that live in a minute. EXECUTE / VERIFY: the orchestrator doesn't write the code, the helpers do. The one exception is a fix of 5 lines or less per task, and only for a bug the verifier found. A cheap haiku verifier re-runs the checks; a sonnet reviewer reads the diff, or an opus security reviewer for security tasks. CLOSE tells me which models actually did the work. Everything lives in a plan file under docs/plans, so I can stop, close the laptop, and run /orchestrate resume the next day. It suggests a commit; it never makes one. /orchestrate · Picking a model

How it picks a model
for each task

Each task scores 0–2 on Ambiguity (how unclear), Breadth (how wide) and Reasoning (how hard). Add them up.

Score or task typeGoes to
0–2haiku
3–4sonnet
5–6Split first; opus only if it can't be split
Security work (auth, secrets, crypto, permissions…)Always opus, plus an opus security reviewer

Its rule: "When unsure, pick the lower tier: escalating costs less than over-provisioning."
A task fails? It retries, then moves up or re-scopes. Still failing: it pauses and tells you.

Take "add a config entry with exact steps": that goes to haiku, because it's clear, one file, little thinking. Three questions per task: how unclear is it, how much does it touch, how hard is it to think through. Zero to two each, add them up. Big tasks get split first. Opus only gets a task that really can't be split, or anything that touches security, like auth, secrets, crypto or permissions. Those always go to opus, and a fresh opus reviewer goes through the diff looking for vulnerabilities. That's why the auth part of the forgot-password task went to opus: because it's security, not because of its score. You can also ask for opus yourself. If a plan has more than 2 opus tasks, it asks you to confirm. The rule I like most is the one on screen. When it's unsure, it picks the cheaper model. If that was wrong, the task fails and moves up. That still costs less than sending everything to the big model just in case. That's where the token saving comes from. I can't give you a number.
