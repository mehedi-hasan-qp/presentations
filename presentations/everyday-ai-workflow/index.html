eqc-kit · The commands

What you run,
and where AI is used

CommandWhat it doesUses AI?
/eqc-checkTurns your doc into a rule list, then one agent per tier checks the code (using a code map, e.g. a graphify graph, first, if yours is up to date). Each rule gets pass / partial / fail / n/a with the file as proof. A plain script works out the level (the highest tier with no fails at or below it). Writes COMPLIANCE.md and a COMPLIANCE.html page.Yes, to check rules. No, to count.
/eqc-fixSuggests what to fix first: low effort, high gain. Small fixes go straight to one helper; big ones get a plan you approve first. Never commits for you.Yes
eqc guardCompares the latest results with the baseline (every rule that has passed). Fails only if one of those stops passing, or the level drops. Known fails don't block you.No
verify + git hooksAn optional shell check (e.g. npm run lint), only for rules a command can test. Runs on commit and push once you opt in with npx eqc-kit hooks.No: too slow, costly and unpredictable for every commit
Four things you run. The top two use AI, the bottom two don't. /eqc-check: the first time, one agent reads your doc and lists every rule by tier. Then one agent per tier goes through the code, in parallel. If you already have a code map, like a graphify graph, it looks there first, but only if the map is newer than your last commit and your uncommitted changes. It never builds or refreshes the map for you, and anything it finds there it confirms in the real code. Then a plain script, no AI, works out the level: the highest tier where that tier and every tier below it have no fails. A fail in the lowest tier is HARD_FAIL. The script never reads your code; it just counts the answers. New: next to the Markdown report you also get an HTML page. One file, no JavaScript, you just open it in the browser. /eqc-fix: it ranks what to fix, low effort and high gain first. Small stuff goes to one fixer. Bigger stuff: opus writes a plan, you approve it, and cheaper models do the typing. It asks before touching CI, packages, architecture or the top tier, and it only runs one fixer at a time. guard: this is the answer to "AI fixed it, then broke it again". Every time results are saved, it remembers which rules passed. That's the baseline, and it only goes up. Guard checks against it. A rule that was already failing won't block you; only something that used to pass and now doesn't. verify: some rules a plain command can check, like "lint is clean". Those rules carry a command, like npm run lint. Not every rule gets one, only the ones a command can check without judgment. The script runs them only for rules that are passing, so a known fail never blocks a commit; only a regression does. CUTTABLE if running late — hooks: opt-in, one command per clone, npx eqc-kit hooks. Commit runs verify; push runs verify, then guard. It won't override hooks you already have, like Husky; it prints the lines to add instead. Anyone can skip hooks with --no-verify, so put the same two commands in CI. Why no AI in the hooks? Too slow, costs money on every commit, and you'd get a different answer each time. Transition: "Enough talking. Let me show you two of these, and the report it writes, on our app." ~2 min

/orchestrate · How it works

How /orchestrate runs a big task,
phase by phase

Five phases: GRILL → PLAN → PREVIEW → EXECUTE / VERIFY → CLOSE. The orchestrator doesn't write the code; helpers on haiku, sonnet or opus do.

PhaseWhat it does
GRILLAsks you questions one at a time, each with a recommended answer. If you have a code map, its helpers search that before grepping. Tiny goals skip this step (fast lane).
PLANSplits the goal into tasks and scores each one (next slide). At most 3 helpers run at once, and each file has one owner.
PREVIEW · the gateShows every task with its score and model, then stops. Only your reply counts: "just go" written into the goal is ignored, and "ok, but…" is an edit.
EXECUTE / VERIFYHelpers build. A haiku verifier runs the checks; a sonnet reviewer reads the diff (an opus security reviewer for security tasks). The orchestrator may make one fix of 5 lines or less per task, only for a bug the verifier found.
CLOSEReports which models did the work. Everything is in a plan file, so you can stop, resume or reject. Never commits on its own.
This is the whole thing in one table. I'll go through it quickly. GRILL is the interview I used to ask for by hand. One question at a time, and it gives you its recommended answer, so most of the time I just say yes. If the goal is tiny, it skips this. PLAN: it splits the goal into tasks and scores each one. Scoring is the next slide. It also decides up front who owns which file, so three helpers working at the same time don't step on each other. PREVIEW is the part I care about most. It shows the full plan and stops. I'll show you that live in a minute. EXECUTE: the orchestrator doesn't write the code, the helpers do. The one exception is a fix of 5 lines or less per task, and only for a bug the verifier found. Then a cheap haiku verifier re-runs the checks, and a separate reviewer reads the diff. CLOSE tells me which models actually did the work. Everything lives in a plan file under docs/plans, so I can stop, close the laptop, and run /orchestrate resume the next day. It suggests a commit; it never makes one. CUTTABLE if running late — the shortcuts it isn't allowed to take. Each one sounds reasonable in the moment. "I'll do this quick fix myself": hand it to a helper. "Approval was given in advance": show the preview anyway. "Small repo, I'll just read it": it reads at most 2 files of 100 lines per phase itself and sends a scout for the rest. "I'll run the tests to be sure": the verifier does that. "This agent sets its own model": pass the model anyway. Transition: "The part of PLAN I want to show you is how it picks the model." ~2.5 min

How it picks a model
for each task

Each task scores 0–2 on Ambiguity (how unclear it is), Breadth (how much it touches) and Reasoning (how hard it is to think through). The total picks the model.

Score or task typeGoes to
0–2haiku
3–4sonnet
5–6Split into smaller tasks first; opus only if it can't be split
Security work (auth, secrets, crypto, permissions…)Always opus, plus an opus security reviewer

You can ask for opus yourself. If a plan has more than 2 opus tasks, it asks you to confirm.
Its rule: "When unsure, pick the lower tier: escalating costs less than over-provisioning."
If a task fails: haiku retries → sonnet retries → one opus try, or the orchestrator re-scopes it → still failing? It pauses and tells you.

Opus only gets a task that really can't be split, or anything that touches security, like auth, secrets, crypto or permissions. Those always go to opus, and a fresh opus reviewer goes through the diff looking for vulnerabilities. The rule I like most is the one on screen. When it's unsure, it picks the cheaper model. If that was wrong, the task fails and moves up. That still costs less than sending everything to the big model just in case. That's where the token saving comes from. I can't give you a number.
